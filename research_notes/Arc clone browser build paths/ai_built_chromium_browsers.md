# AI-agent-built Chromium browsers (2025-2026), with fork suitability for Radian

Research date: 2026-10-22. Repo metadata (stars, dates, licenses, commit trailers) was pulled live through the GitHub API (`gh api`) on that date. "AI share" is measured from `Co-Authored-By:` / `Claude-Session` trailers in each repo's last 100 commits, because no author gave a percentage. Radian's constraints are an M4 with 16 GB RAM, 17 GB free disk and no Xcode.

## Which Chromium forks or Chromium-embedding browsers have been built substantially with AI agents?

### Takeaway
Six public Arc-style projects show heavy, verifiable AI-agent authorship in 2026: Stedding, Mori, Refrax, Vela, Orbe and nyshk97/browser. Yalqen and BrowserOS show some. Only three of them compile Chromium itself: Stedding (a patch series), Mori (a SwiftUI overlay) and Refrax (a patched Chromium engine bundle). The rest are Electron apps. Helium, the most popular de-Googled fork, bans AI-agent contributions outright. Atlas, Comet and Dia are closed source and cannot be forked.

### Cited Findings
**Chromium forks / Chromium compiled from source**

Created 2026-08-30; last push and release v0.3.0-beta.5 on 2026-10-22, with arm64 DMG and Windows x64 EXE. 20 stars, 0 forks, BSD-3-Clause. — [GitHub API / repo](https://github.com/ysalitrynskyi/stedding-browser); [Releases](https://github.com/ysalitrynskyi/stedding-browser/releases)

**Closed-source agentic browsers (cannot be forked)**
- **ChatGPT Atlas** embeds Chromium through "OWL": Chromium's browser process runs outside the Atlas app process and talks to it over Mojo, with custom Swift and TypeScript Mojo bindings. OWL ships as a prebuilt binary, so engineers rarely build Chromium locally. The post's authors are Ken Rockot and Ben Goodger. — [OpenAI, "Building ChatGPT Atlas"](https://openai.com/index/building-chatgpt-atlas) (read via search excerpt; direct fetch returned HTTP 403); [ByteByteGo summary](https://blog.bytebytego.com/p/the-architecture-behind-atlas-openais)
- **Comet** (Perplexity, launched July 2025) is built on Chromium and supports Chrome extensions. — [SiliconANGLE 2025-07-09](https://siliconangle.com/2025/07/09/perplexity-introduces-comet-browser-ai-powered-automation-tools/); [OpenSourceForU](https://www.opensourceforu.com/2025/10/perplexitys-free-ai-browser-comet-takes-aim-at-google-chrome-and-openai/)
- **Arc / Dia:** Arc has received no new features since May 2025, and its developer has shifted to Dia. — [Wikipedia: Arc](https://en.wikipedia.org/wiki/Arc_(web_browser))

**Upstream Chromium itself**
- Chromium's tree now has an `agents/` directory "for files related to AI coding agents (e.g. `gemini-cli`)": shared `GEMINI.md` prompts, approved MCP servers and skills. It also has a `.claude/skills` directory. — [chromium/agents/README.md](https://github.com/chromium/chromium/tree/main/agents)
- `agents/ai_policy.md` requires authors to "self-review and understand all code" and warns that committers who send CLs they do not understand risk losing committer status. — [ai_policy.md](https://github.com/chromium/chromium/blob/main/agents/ai_policy.md)

### Inferences
- Stedding is almost certainly developed with Claude Code: `CLAUDE.md` imports AGENTS.md, and the docs name `run_in_background` and the 10-minute tool-call cap. It deliberately hides the attribution, so the AI share cannot be quantified.
- Mori's verifiable agent is Claude (Opus 4.8). The "built with Codex" lead is unconfirmed; Codex is a runtime feature, not visibly the build agent.
- "Arc clone built by Claude in 2026" is now a recognisable genre. Most entries pick Electron because it avoids the Chromium build entirely.

### Gaps
- I found no "I built a Chromium browser with Claude Code/Codex" write-up on HN or Reddit, and no YouTube video. Searches returned only Claude-in-Chrome extension material. X/Twitter was not searchable with these tools.
- Not verified: who built Dia and Comet internally, or whether any AI agents were used on them; whether OpenAI used Codex on Atlas. The Atlas post could not be fetched directly.
- No AI-attribution check was run on evil's commits.

## Per-project details: stack, build, requirements, extensions, license, activity, AI share, Arc-likeness

### Takeaway
Every real Chromium build documented here needs full Xcode, roughly 100-200 GB of disk and hours of compile time. None fits Radian's 17 GB free disk with no Xcode. Stedding is the most Arc-complete and best-documented Chromium fork. Mori is the most "native SwiftUI Arc", but its repo cannot be reproduced on its own.

### Cited Findings
**Stedding**
- UI: Chromium Views C++, plus WebUI for settings. It is a patch series on Chromium stable (README badge: Chromium 156; latest build 156.0.8078.48) and lists the source change for each feature. — [README](https://github.com/ysalitrynskyi/stedding-browser)
- UI work stays "as high in the stack as possible (views, WebUI, top chrome)". Electron/CEF and Firefox bases were rejected. — [ADR 0003](https://github.com/ysalitrynskyi/stedding-browser/blob/main/docs/decisions/0003-chromium-minimal-patch-fork.md)
- The sidebar rides upstream's `VerticalTabStripRegionView`, with any look divergence in a subclass. It does not fork `TabStrip`. — [ADR 0010](https://github.com/ysalitrynskyi/stedding-browser/blob/main/docs/decisions/0010-ride-upstream-vertical-tabs.md)
- `patches/` holds 83 numbered patches (0001-0083), about 10.9 MB in total. Several are very large: 0057 is 1.37 MB, 0072 1.12 MB, 0071 756 KB, 0077 726 KB. — [patches/](https://github.com/ysalitrynskyi/stedding-browser/tree/main/patches)
- Build steps: `bootstrap-depot-tools` → `sync-chromium` → `apply-patches` → `apply-branding` → `build-chromium release` → `package-dmg`. The README says it needs "Apple silicon, about 150 GB free and a few hours the first time". — [README](https://github.com/ysalitrynskyi/stedding-browser)
- Requirements: full Xcode, not just the Command Line Tools. `sync-chromium` refuses to start below 150 GB free. Measured checkout 65 GB; a release build adds 9.3 GB. RAM: "16 GB is the practical floor… cap parallelism… `autoninja -j4`". — [docs/ARCHITECTURE.md](https://github.com/ysalitrynskyi/stedding-browser/blob/main/docs/ARCHITECTURE.md)
- Measured times on an M1 Max with 64 GB: first cold release build 3 h 29 min; first official (PGO + ThinLTO) build 4 h 5 min; re-sync from nothing 43 min. Remote execution is unavailable (`use_remoteexec = false`). — [docs/ARCHITECTURE.md](https://github.com/ysalitrynskyi/stedding-browser/blob/main/docs/ARCHITECTURE.md)
- CI: "GitHub-hosted runners cannot practically build Chromium". Hosted CI only runs shellcheck and repo hygiene, a weekly check that the series applies to the pin (`apply-patches --check`), and a daily pin-staleness issue. Releases are built by hand on a Mac and a Windows PC. — [ARCHITECTURE.md "CI reality"](https://github.com/ysalitrynskyi/stedding-browser/blob/main/docs/ARCHITECTURE.md); [series.yml](https://github.com/ysalitrynskyi/stedding-browser/blob/main/.github/workflows/series.yml)
- Extensions: "Full Chrome extension compatibility is a hard requirement". — [AGENTS.md](https://github.com/ysalitrynskyi/stedding-browser/blob/main/AGENTS.md)
- Arc parity it has: sidebar at Arc proportions, essentials, pinned tabs that return home on ⌘W, nested folders (also among pins), Spaces with colours and per-Space cookie partitions, ⌘T command bar plus ⇧⌘P, split view by drag, Little windows (Mac), routing (Air Traffic Control-style), sleep, archive, and one-click Arc import (Mac).
- Arc parity it lacks: Peek (off until rebuilt), Boosts and Easels (deferred), mini player, Library/Live Folders, sync, and AI (never).
- Known product limits: no Widevine and no Safe Browsing; Intel Mac and Linux unsupported. — [README](https://github.com/ysalitrynskyi/stedding-browser)

**Mori**
- UI: SwiftUI + AppKit chrome with an Objective-C++ bridge, compiled into the `chrome` target of an ungoogled-chromium checkout. Chromium keeps tabs, navigation, extensions, downloads and permissions. — [README](https://github.com/FujiwaraChoki/mori-browser); [docs/ARCHITECTURE.md](https://github.com/FujiwaraChoki/mori-browser/blob/main/docs/ARCHITECTURE.md)
- The repo tracks 110 files. Apart from top-level docs, everything is under `ungoogled-chromium-macos/build/src/chrome/browser/ui/mori/`: about 70 Swift files, 4 `.mm` files (bridge 69.6 KB, window 36.5 KB, extensions 35.7 KB, permission prompt 4.6 KB), headers and assets. There are no `.gn`, `.patch` or `.cc` files anywhere. — [repo tree](https://github.com/FujiwaraChoki/mori-browser/tree/main/ungoogled-chromium-macos/build/src/chrome/browser/ui/mori)
- The docs say the Swift files "are compiled by the `mori_ui_swift` target in `chrome/browser/ui/BUILD.gn`", but that file is not in the repo. — [docs/SOURCE_LAYOUT.md](https://github.com/FujiwaraChoki/mori-browser/blob/main/docs/SOURCE_LAYOUT.md)
- `mori_chrome_hooks.h` says `OnBrowserWindowCreated` is "Called from MoriBrowserWindow's ctor/dtor and Show()". Nothing in the repo shows where Chromium is changed to construct `MoriBrowserWindow`. — [mori_chrome_hooks.h](https://github.com/FujiwaraChoki/mori-browser/blob/main/ungoogled-chromium-macos/build/src/chrome/browser/ui/mori/mori_chrome_hooks.h)
- Build prerequisites: "macOS with Xcode installed at /Applications/Xcode.app" and "The Chromium checkout and generated `out/Default` build directory already present". Build command `ninja -j 16 -l 24 -C out/Default chrome`, then `ditto` to `~/Downloads/MoriBrowser.app`. No disk, RAM or time figures are given. — [BUILDING.md](https://github.com/FujiwaraChoki/mori-browser/blob/main/BUILDING.md)
- BUILDING.md says the repo "now contains the Mori browser work on top of ungoogled-chromium instead of the old CEF app", so it was earlier a CEF prototype. — [BUILDING.md](https://github.com/FujiwaraChoki/mori-browser/blob/main/BUILDING.md)
- Arc parity: Spaces ("contexts") and folders, Air Traffic Control routing, Peek, Boosts (CSS/JS + zap), ⌘T launcher, sleep and archive, gradient themes, Reader, passkeys, PiP media controls, and a Codex AI panel. The README does not list split view or Little Arc.
- Extension support goes through `mori_chrome_extensions.mm` and `ExtensionsMenu.swift`. The README marks Mori as experimental and a security risk. — [README](https://github.com/FujiwaraChoki/mori-browser)

**Refrax**
- Architecture: a Swift/AppKit browser that owns all state. "System WebKit is built in; every other engine is a separately installed bundle" (`<Name>.engine`), using a message contract defined in `SDK/RFXEngine.h`. — [Engines/CONTRACT.md](https://github.com/kageroumado/refrax-browser/blob/main/Engines/CONTRACT.md)
- The Chromium engine is built from ungoogled-chromium plus 7 Refrax patches (message-pump attach to the host `NSApplication`, a host content-browser client, tab helpers without a `Browser`, and others), with "Code that can live outside upstream files" in `//refrax`. — [Engines/Chromium/patches/README.md](https://github.com/kageroumado/refrax-browser/blob/main/Engines/Chromium/patches/README.md)
- End users download the engine in Settings → Engines. Requirements: macOS 26+ and Xcode 26+ for development. Features: vertical tabs, spaces, groups, routing rules, command palette, Touch ID-locked spaces, and the `refrax-ctl` CLI for agents. — [README](https://github.com/kageroumado/refrax-browser)

**BrowserOS**
- Monorepo layout: `packages/browseros` (Chromium patches + `series_patches` + Python build CLI) and an agent platform in TypeScript/Rust. The new-tab and side-panel UI is a WXT + React extension. The browser needs about 100 GB of disk. It uses some ungoogled-chromium patches. — [README](https://github.com/browseros-ai/BrowserOS)
- It is AGPL-3.0, an AI-agent browser rather than an Arc-UI browser. Chrome extensions work. — [README](https://github.com/browseros-ai/BrowserOS)

**Helium**
- Built on ungoogled-chromium with 346 `.patch` files, including `patches/helium/ui/layout/vertical.patch` and `split-view.patch`. GPL-3.0. Latest releases: 0.20.1 (2026-10-21) and macOS 0.20.1.1 (2026-10-22). — [imputnet/helium](https://github.com/imputnet/helium); [helium-macos releases](https://github.com/imputnet/helium-macos/releases)
- macOS builds run on Depot-sponsored runners. — [helium-macos README](https://github.com/imputnet/helium-macos)

**Sessionat**
- Recommends "32 GB RAM (linking the framework needs ~28 GB), 200 GB free SSD", with a 3-8 h first build. Its repo is source-file replacements over vanilla Chromium. — [README](https://github.com/dublyo/sessionat)
- Its spec puts the sidebar in `chrome/browser/ui/views/frame/` (`SessionatSidebarView`). — [ARCHITECTURE.md](https://github.com/dublyo/sessionat/blob/main/ARCHITECTURE.md)

**evil**
- Requirements: "16 GB of RAM and 100 GB of free disk"; first build "two to six hours; incremental builds take minutes". — [README](https://github.com/evil-browser/evil)

**Vela** (Electron)
- Features: Spaces, favorites, pinned nested folders, Today tabs with auto-archive, ⌘T, Peek, 2-4-pane split, Little Vela windows, Boosts with Zap, Air Traffic Control, one-click Arc import, and Chrome Web Store installs ("Add to Vela").
- The README's own benchmark claims 271 ms launch vs Arc's 2058 ms. — [README](https://github.com/JoSanson/vela)

**Orbe** (Electron)
- Arc import (Spaces, pins, folders), Chrome Web Store installs with signature checks, Easels-like "Tableaux", and ⌘W-archive. The Electron engine is downloaded on first launch into `~/.orbe-dev`. — [README](https://github.com/amadoubaui/orbe)

### Inferences
- Stedding's "minimal patch-set" label no longer holds: 10.9 MB across 83 patches, with single patches over 1 MB. Rebases onto each Chromium stable will be heavy, though it does have tooling (`fold-fix`, `update-patches`, `check-pin`).
- Mori cannot be reproduced from its repo alone. A fork would have to recreate the GN target (`mori_ui_swift` in `chrome/browser/ui/BUILD.gn`) and the Chromium-side hook that makes Chromium create `MoriBrowserWindow` instead of `BrowserView`. That second part is deduced from the headers.
- Refrax's design, like Atlas's OWL, lets end users and UI developers avoid building Chromium. That suits low-disk machines, but Refrax is GPL-3.0, needs Xcode 26, and someone still has to build the engine bundle.
- The Electron projects need no Xcode or Chromium checkout. Their extension support is partial (built from `electron-chrome-extensions` plus polyfills), not full Chrome parity.

### Gaps
- Mori's incremental build time, disk use and RAM are undocumented.
- Not checked: whether Mori's `.gitignore` hides further tracked edits, and the actual hook call sites in Chromium. A clone and `git log --all` would settle both.
- Refrax's Chromium engine disk and build requirements were not found (no workflows directory; `setup.sh` had no Chromium references). Its Arc-feature depth beyond the README was not checked.
- The Electron projects' claimed extension and Arc-import coverage was not tested. Not verified: BrowserOS vertical tabs and spaces.
- No project reports an incremental build time for a single changed `.cc` file. Stedding lists it as "TBD".

## What workflows did builders describe for using AI agents on a codebase as big as Chromium?

### Takeaway
The documented patterns are:
- Keep first-party code in an overlay directory or a feature-organised patch series.
- Ride upstream features instead of replacing them.
- Fold every fix into the patch that owns it.
- Run multi-hour builds as detached, budgeted jobs, not polled ones.
- Use DCHECK-enabled release builds for minute-scale rebuilds.
- Put CI only on cheap checks (patch application and pin staleness), since hosted runners cannot build Chromium.

### Cited Findings
- **Stedding's loop:** "research → spec → failing test → implement → build → test → use it → patch → commit". Fixes go into the owning patch via `tooling/fold-fix`, and commits carry `Why:` / `Removable when:` footers. The series is organised by feature, not by date. — [docs/AGENT-LOOP.md](https://github.com/ysalitrynskyi/stedding-browser/blob/main/docs/AGENT-LOOP.md)
- **Stedding's numbers:** a DCHECK + dangling-pointer build takes 3 h 20 min from nothing and "3 min to rebuild after an edit" (it found 12 defects). An ASan build takes 5 h from nothing and 15 min to rebuild (1 use-after-free). A debug build found nothing extra. — [docs/AGENT-LOOP.md](https://github.com/ysalitrynskyi/stedding-browser/blob/main/docs/AGENT-LOOP.md)
- **Stedding's rules for long jobs:**
  - "Supervise long jobs; do not poll them". The budget is "a dead-man's switch… Chunks of 45 minutes".
  - Collect every failure per run ("one pass should find everything"), because fixing one per rebuild "cost a dozen rebuild-and-run cycles".
  - Use `git grep`, because `grep -r` timed out four times. — [docs/AGENT-LOOP.md](https://github.com/ysalitrynskyi/stedding-browser/blob/main/docs/AGENT-LOOP.md); [AGENTS.md](https://github.com/ysalitrynskyi/stedding-browser/blob/main/AGENTS.md)
- **Stedding's guardrails:** ask the operator once, up front, for permissions; no push or release without a yes in chat; numbers in docs must come from `tooling/dev status`, never be hand-typed; unmeasured claims are written `TBD`. — [AGENTS.md](https://github.com/ysalitrynskyi/stedding-browser/blob/main/AGENTS.md)
- **Stedding cuts patch weight by riding upstream:** upstream already ships vertical tabs (`kVerticalTabsLaunch` enabled by default), so the sidebar subclasses that view. The ADR measured churn of 412 commits/year on `browser_view.cc`, which makes replacing it costly. — [ADR 0010](https://github.com/ysalitrynskyi/stedding-browser/blob/main/docs/decisions/0010-ride-upstream-vertical-tabs.md)
- **Stedding's licence hygiene for Arc-alike ideas:** ideas taken from copyleft Nook (GPL-3.0) and Aura (MPL-2.0) are "rebuilt from scratch, from written descriptions; nothing of theirs is copied", to keep the BSD core clean. — [ADR 0021](https://github.com/ysalitrynskyi/stedding-browser/blob/main/docs/decisions/0021-ideas-from-nook-and-aura.md)
- **Mori's overlay pattern:** all first-party code lives in one flat directory inside Chromium. The bridge stays thin: "If logic is UI state or product behavior, keep it in Swift. If logic requires Chromium browser objects, keep it in Objective-C++."
  - The incremental loop is `ninja -C out/Default chrome`, then repackage the app.
  - Agent rules: use `trash`, never `rm -rf`; use the Playwright CLI for browser automation. — [AGENTS.md](https://github.com/FujiwaraChoki/mori-browser/blob/main/AGENTS.md); [docs/ARCHITECTURE.md](https://github.com/FujiwaraChoki/mori-browser/blob/main/docs/ARCHITECTURE.md)
- **Refrax's minimal-hook pattern:** the 7 patches touch upstream files only where unavoidable, for example linking `//refrax/host` into `chrome_dll` from `chrome/BUILD.gn` to avoid a dependency cycle. Everything else lives in `//refrax`. — [Engines/Chromium/patches/README.md](https://github.com/kageroumado/refrax-browser/blob/main/Engines/Chromium/patches/README.md)
- **Vela's autonomous-agent protocol (Electron):**
  - Resume from the first unchecked box in `PROGRESS.md`.
  - A task is done only when the automated test is green, a Playwright screenshot has been inspected, and the box is checked with the commit hash.
  - Log ambiguity in `DECISIONS.md`; if blocked for more than 30 minutes, take the simplest workaround and move on. — [CLAUDE.md](https://github.com/JoSanson/vela/blob/main/CLAUDE.md)
- **Atlas:** shipping OWL as a prebuilt binary means engineers "rarely build Chromium locally". — [OpenAI](https://openai.com/index/building-chatgpt-atlas) (search excerpt)
- **Upstream Chromium** provides shared agent prompts, MCP servers and skills under `//agents`, and an AI policy that requires human understanding of every CL. — [chromium/agents](https://github.com/chromium/chromium/tree/main/agents)

### Inferences
- A one-person, AI-agent Chromium project is feasible, as Stedding shows: 83 patches and 2 platforms in about 8 weeks (2026-08-30 to 2026-10-22). But it relied on 150 GB disks, a 64 GB M1 Max, a Windows PC, and builds of 3-5 hours.
- On a 16 GB, 17 GB-free M4 without Xcode, the only viable Chromium paths are:
  - an external SSD plus installing Xcode;
  - a rented cloud Mac or self-hosted runner;
  - an OWL/Refrax-style split, where a prebuilt Chromium host is built once elsewhere and the UI shell is iterated locally.

### Gaps
- No builder published token or cost figures, or an agent-versus-human code split.
- None of these projects has a public write-up describing ccache, remote builds, or an incremental `.cc` rebuild time on Apple silicon.

## Which project is the most complete, reproducible-from-repo, and permissively licensed base for an Arc-identical browser?

### Takeaway
Stedding is the clear winner on all three criteria: BSD-3-Clause, the full patch series and build scripts are in the repo, and it is the most Arc-complete, with signed macOS releases on 2026-10-22. Mori (MIT) is the best reference for a native SwiftUI Arc look, but it is not reproducible from its repo. Neither can be built on Radian's current machine.

### Cited Findings
- **Stedding:**
  - License: BSD-3-Clause, with a recorded decision that "the core stays BSD". — [AGENTS.md](https://github.com/ysalitrynskyi/stedding-browser/blob/main/AGENTS.md); [ADR 0002 listing](https://github.com/ysalitrynskyi/stedding-browser/tree/main/docs/decisions)
  - Reproducible from the repo via the `tooling/*` scripts (sync, apply, brand, build, package). — [README](https://github.com/ysalitrynskyi/stedding-browser)
  - One spec per feature, each behaviour with a test id, in `docs/features/`. — [README](https://github.com/ysalitrynskyi/stedding-browser)
  - Arc gaps: Peek, Boosts, Easels, mini player, Live Folders, sync, AI. — [README](https://github.com/ysalitrynskyi/stedding-browser)
- **Mori:** MIT, SwiftUI, with Peek and Boosts that Stedding lacks. But the repo is an overlay only: the `BUILD.gn` target and the Chromium hook are not included, and BUILDING.md assumes an existing checkout and `out/Default`. — [BUILDING.md](https://github.com/FujiwaraChoki/mori-browser/blob/main/BUILDING.md); [SOURCE_LAYOUT.md](https://github.com/FujiwaraChoki/mori-browser/blob/main/docs/SOURCE_LAYOUT.md)
- **The others:**
  - Refrax: GPL-3.0, WebKit-first with a pluggable Chromium. — [repo](https://github.com/kageroumado/refrax-browser)
  - Helium: GPL-3.0 and bans AI work. — [AGENTS.md](https://github.com/imputnet/helium/blob/main/AGENTS.md)
  - BrowserOS: AGPL-3.0 and not Arc-UI. — [repo](https://github.com/browseros-ai/BrowserOS)
  - Vela, nyshk97/browser: GPL-3.0 Electron. — [Vela](https://github.com/JoSanson/vela); [nyshk97](https://github.com/nyshk97/browser)
  - Orbe and Yalqen: MIT Electron. — [Orbe](https://github.com/amadoubaui/orbe); [Yalqen](https://github.com/YSamed/yalqen)
- **Sessionat:** MIT and Chromium-based with an Arc-style Workspaces sidebar, but dormant since 2026-06-05 and recommending 32 GB RAM and 200 GB disk. — [repo](https://github.com/dublyo/sessionat)

### Inferences
- **Radian ranking:**
  1. Stedding as the fork base, if Radian accepts Views C++ UI and can get about 150 GB of external disk, full Xcode and a 3.5 h-plus first build.
  2. Mori as a design and code reference for a SwiftUI chrome. Its MIT code can be lifted into a Stedding-like reproducible series once the GN and hook pieces are rewritten.
  3. If no Chromium build is acceptable at all, Orbe (MIT) or Yalqen (MIT) as an Electron base, accepting partial extension support. Vela is the most Arc-complete Electron option, but GPL-3.0.
- Mixing licenses: MIT (Mori) code can go into a BSD-3 fork. GPL code (Refrax, Vela, Helium) cannot, without making Radian GPL.
- Stedding's own disk floor (150 GB) is nearly 9 times Radian's free space. The deciding constraint for Radian is build infrastructure, not the choice of base.

### Gaps
- Not done: a clean-machine reproduction of Stedding or Mori. That would need about 150 GB and many hours, outside this read-only scope.
- Not verified: Stedding's Chrome Web Store install flow, and Mori's extension coverage.
- Not checked: whether Stedding's patches apply cleanly on a different pin. Its weekly `series` workflow is the only evidence.
